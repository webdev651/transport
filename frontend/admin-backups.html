Database recovery procedure

Recovery replaces the data in the database with the data in the backup. Anything entered after the backup was taken is lost, so use the newest good backup and tell users before you start.
  1. Open the Backup history tab, choose the backup, and press Verify. Only use a backup that shows “OK”.
  2. Download it, or copy it from the server’s backup folder. Keep a copy somewhere other than the server.
  3. Turn on maintenance mode (Settings → Maintenance) and stop the TransitPass server, so nothing writes while the data is replaced.
  4. On the server, in the backend folder, run a dry run first. It checks the file’s checksum and shows what it contains:
    node scripts/restore-backup.js backups/<file>.sql.gz
  5. Restore for real. A safety backup of the current database is taken first, automatically:
    node scripts/restore-backup.js backups/<file>.sql.gz --yes
  6. To rehearse safely, restore into a separate scratch database instead:
    node scripts/restore-backup.js backups/<file>.sql.gz --database transitpass_restore_test --yes --no-safety-backup
  7. Start the server, sign in, check a few records, then turn maintenance mode off.

How backups are protected

  • Files are stored outside the public web folder (BACKUP_DIR) and the server refuses to start a backup if that folder is placed inside it.
  • Only a signed-in administrator can download one, and every download is recorded in the activity log.
  • Each file has a SHA-256 checksum, so damage or tampering is detected by Verify and by the restore script.
  • Backups contain personal data and password hashes: store copies like any confidential record.
